# ADR 0001 — Workspace layout, toolchain and protobuf tooling

* Status: accepted (S0, 2026-11-02)
* Spec: §3, §11, §15

## Context

New repository. The spec prefers a Rust Cargo workspace (modular monolith + isolated SFU),
Protobuf for versioned wire messages and reproducible builds.

## Decision

1. **Cargo workspace**, resolver 3, edition 2024. Layout follows spec §15 but crates are
   created only when the stage that owns them starts (no empty placeholder crates):
   S0 has `apps/desktop`, `apps/app-server`, `crates/protocol`, `crates/media-transport`,
   `benchmarks/harness`, `tools/media-probe`.
2. **Toolchain pinned** in `rust-toolchain.toml` to `1.99.1` (stable on 2026-11-02) with
   rustfmt + clippy. `Cargo.lock` is committed; CI uses `--locked`.
3. **Protobuf**: schemas in `proto/`, Rust types generated by `prost-build` 0.14, `.proto`
   parsed by **`protox`** (pure Rust). No system `protoc` is required on any developer
   machine or CI runner.
4. Workspace lints: `unsafe_code = "deny"` (FFI modules opt out locally with a SAFETY
   comment), clippy `-D warnings` in CI.
5. Release profile: thin LTO, `codegen-units = 1`, `strip`, `panic = "abort"` (size/RAM
   targets §13). Dev profile keeps debug info only for workspace crates (the dev
   machine's system drive is nearly full; full debug info produced a 7.4 GB target dir).

## Consequences

* Builds need only `rustup` + a platform C toolchain (MSVC on Windows, Xcode CLT on macOS,
  gcc + listed `-dev` packages on Linux, see CI).
* `panic = "abort"` means panics in worker threads terminate the process in release;
  long-running components must not panic on bad input (validated at the boundary).
